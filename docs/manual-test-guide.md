# 车队配件库存管理系统 - 手工全流程测试手册

> 用途：测试人员按「左侧菜单 → 页面按钮」的顺序，走完一遍真实业务闭环，验证功能、单据状态流转、库存与报表联动是否一致。
> 说明：本文只描述**操作路径与预期现象**（定性），不写死具体数量/金额。每次执行时用自己录入的数据自行核对「方向是否正确、是否对得上」。

## 一、测试目标

| 编号 | 目标 | 验证方式 |
|---|---|---|
| G1 | 主数据可维护 | 分类、配件、车型、车辆、供应商、仓库、库位、用户 全部能增删改查 |
| G2 | 单据状态机正确 | 入库/出库/调拨/盘点/工单 只能按合法状态流转，非法操作被拦截 |
| G3 | 库存联动正确 | 入库增加、出库减少、调拨在途与落地、盘点差异调整，库存件状态同步 |
| G4 | 报表与看板一致 | 库存报表、流水报表、单车成本、首页看板与业务单据能对上 |
| G5 | 扫码与打印可用 | 配件条码、库位二维码、库存件二维码可被扫码枪/摄像头识别并正确带入 |
| G6 | 权限与日志可用 | 不同角色操作范围符合预期；关键操作均可追溯到操作日志 |

## 二、测试环境准备

1. **启动服务**
   - 后端：`http://127.0.0.1:8080`（Swagger 文档可访问，用于出现异常时对照接口返回）
   - 前端：`http://127.0.0.1:5173`
2. **登录账号**
   - 管理员：`admin / admin123`（具备全部权限，主流程用它）
   - 另需准备：`keeper`（库管员）、`readonly`（只读）各一个，用于权限验证（可在「系统管理 → 用户管理」新建）
3. **浏览器**
   - Chrome / Edge 最新版；允许页面弹窗与打印（打印标签需要）
   - 开一个无痕窗口专门登录只读账号，避免反复切换 token
4. **扫码设备**
   - 方式一：USB 扫码枪（键盘模拟输入，扫完自动回车）——最接近现场
   - 方式二：手机摄像头扫码（页面扫码组件）
   - 方式三：手工把二维码内容（配件编码 / 库存件编码 `item_code` / 库位编码）粘贴进扫码框后回车
5. **数据命名约定**（便于识别与清理，务必统一）
   - 统一前缀：`MAN-<日期>`，例如 `MAN-1024-001`
   - 配件编码、配件名称、车辆车牌、供应商名称、库位编码都带该前缀
   - 建议单独建一个测试仓库（如 `MAN-1024-中转仓`）与测试库位，避免污染正式数据
6. **记录基线（重要）**
   - 开工前到「库存管理 → 库存查询」按测试配件 + 测试仓库筛选，记录当前账面**数量/金额**（或直接确认该配件在该仓为 0）
   - 后续每一步只核对「是否按预期增减」，不必强求某个具体数字

每条用例记录 4 列，最后汇总：

| 用例编号 | 菜单路径 | 操作要点 | 预期结果 | 实际结果 | 结论 |

通过标准：
- 页面无白屏、无控制台报错、无 500
- 业务拦截有明确中文提示（不是空白报错或 toast 一闪而过）

### 阶段 1：入库（建立库存的起点）

菜单：**入库管理**（列表页）→ 「新建入库单」

#### 1.1 新建入库单-扫码与手工两条路径（TC-IN-01）

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 进入新建页，先不填任何明细直接「提交审核」 | 拦截并提示请先扫码或手动添加入库明细 |
| 2 | 表头选择：供应商（0.6 建的）、入库仓库（`MAIN`）、入库类型=`采购入库`、备注 | 下拉数据来自基础资料，可搜索 |
| 3 | 用扫码枪扫**普通配件（不追踪）**的二维码 | 明细表自动追加一行，数量默认为 1 |
| 4 | 再扫同一个配件一次 | 不新增行，该行数量 +1（提示已存在的配件数量 +1） |
| 5 | 用扫码枪扫**按件追踪配件**的二维码 | 明细追加该配件；数量可填 1 件或多件，审核后按数量**逐件**生成库存件与二维码 |
| 6 | 点「手动添加」选择配件 | 也能追加明细（包括按件追踪配件）；区别是扫码会记录扫码内容，手工添加不带扫码信息 |
| 7 | 在明细行修改：数量、单价（金额自动重算）、批次号、生产/到期日期、库位（0.8 建的） | 金额随数量×单价联动；库位可选 |
| 8 | 「删除」某一行明细 | 该行移除；「清空明细」清空全部 |
| 9 | 扫码一个不存在的条码 | 提示无法识别，建议用「手动添加」，不产生脏数据 |

#### 1.2 草稿 / 提交 / 审核 / 作废 状态流转（TC-IN-02）

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 填好明细后点「保存草稿」 | 回到列表；该单状态=**草稿**；库存不变（库存查询中该配件数量/金额无变化） |
| 2 | 列表「详情」打开草稿单 | 详情页只提供「提交审核 / 作废」两个动作，**没有编辑入口**（要改明细需作废后重建，属当前实现，验收时确认交互不自相矛盾） |
| 3 | 详情页点「提交审核」 | 状态=**待审核**；此时明细不可再改 |
| 4 | 待审核状态下再次点「提交审核」 | 按钮不再出现（或点击被拦截并提示状态不允许） |
| 5 | 列表点「审核」（或详情页「审核通过」） | 状态=**已入库**；系统按明细生成库存（按件追踪配件逐件生成库存件/二维码） |
| 6 | 审核通过后回到「库存查询」 | 该配件在该仓库数量、金额**按本次明细增加**；库位显示为录入的库位 |
| 7 | 「库存件查询」筛选该配件 | 按件追踪配件出现与入库数量一致的库存件记录，状态=在库 |
| 8 | 另建一张入库单，在草稿态点「作废」 | 状态=**已作废**；库存不变；作废单不可再提交/审核 |
| 9 | 另建一张入库单，**提交审核后**再作废 | 允许作废（详情页作废按钮在草稿与待审两种状态都可用）→ 状态=**已作废**；库存不变 |
| 10 | 尝试备注输入超过 255 字 | 输入框限制长度 |

#### 1.3 入库标签打印（TC-IN-03）

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 入库单列表/详情点「打印标签」 | 打开标签预览（或打印页），包含配件编码/名称/二维码 |
| 2 | 打印预览（Ctrl+P 查看） | 标签内容完整、不被截断、无多余页 |
| 3 | 用扫码枪扫打印出来的二维码 | 内容能被入库/出库扫码框正确识别（对应配件或库存件） |

### 阶段 2：库存与标签校验

#### 2.1 库存查询（TC-INV-01，菜单：库存管理 → 库存查询）

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 按库存件编码 / 二维码 / 序列号 / 批次号 / 配件 / 仓库 / 库位 / 状态 分别筛选 | 各条件独立生效；组合条件为「与」关系 |

### 阶段 3：维修工单（出库领料的前置）

菜单：**维修工单**（单页，新建/详情均为弹窗）

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 「新建工单」：选择车辆（0.5 建的车）、维修类型、维修负责人、进厂时间、故障描述、备注 | 保存成功，列表新增，状态=**待修**；工单号自动生成 |
| 2 | 不选车辆直接保存 | 必填校验拦截 |
| 3 | 对待修工单点「编辑」修改故障描述 | 可编辑并保存 |
| 4 | 点「开始维修」 | 状态=**维修中**；此时「开始维修」按钮消失/置灰 |
| 5 | 维修中对同一工单再次操作「编辑」 | 按当前实现应禁止修改（或仅允许受限字段），必须给出明确提示 |
| 6 | 去「车辆列表」→ 该车「维修记录」 | 能看到这条维修中的工单 |
| 7 | 回到工单列表点「详情」 | 显示工单信息 + 配件明细（此时为空）+ 配件成本/工时费/合计（初始为 0 或空） |
| 8 | 见阶段 4：用「关联工单」出库领料后，再回来看该工单详情 | 配件明细出现领用的库存件/配件，**配件成本自动累加**为领用金额 |
| 9 | 点「完工」 | 状态=**已完工**；出厂时间被记录 |
| 10 | 点「结算」→ 弹窗填工时费 → 「确认结算」 | 状态=**已结算**；合计=配件成本+工时费；已结算工单不可再改 |
| 11 | 待修/维修中工单直接点「结算」 | 被拦截（需先完工） |

> 注意：工单是「配件成本」的唯一来源之一，阶段 7 单车成本报表要与这里的金额对上。

### 阶段 4：出库（维修领用 → 库存扣减）

菜单：**出库管理** → 「新建出库单」

#### 4.1 创建出库单（TC-OUT-01）

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 进入新建页，**未选出库仓库**就扫码 | 提示请先选择出库仓库再扫码 |
| 2 | 表头：出库仓库=`MAIN`、出库类型=`维修领用`、关联车辆=测试车、关联工单=阶段 3 的维修中工单、领用人、备注 | 下拉可搜索；**选择关联工单后关联车辆会自动带出**，两处车辆信息保持一致 |
| 3 | 扫码**按件追踪配件**的库存件二维码（阶段 1/2 打印的标签） | 明细自动追加，库存件编码带入，数量=1，单位成本带出 |
| 4 | 再扫同一个库存件二维码 | 提示该库存件已添加/已出库，不重复追加 |
| 5 | 扫**非追踪配件**的编码 | 提示无法识别的条码（非追踪配件请改用「手动添加」） |
| 6 | 「手动添加」非追踪配件，填数量 | 追加明细；数量可改，金额=数量×单位成本 |
| 7 | 修改某行数量为 0 或负数 | 校验拦截（数量下限 0.01） |
| 8 | 扫一个属于**其它仓库**的库存件 | 提示仓库不一致，不能出库 |
| 9 | 扫一个**已出库/已报废/已盘亏**的库存件 | 提示该库存件状态不可出库（业务错误码 2002/2003 类提示） |
| 10 | 扫一个不存在的编码 | 提示无法识别条码 |
| 11 | 用测试车 + 工单组合，故意让明细数量超过当前库存 | 提交或审核时被拦截，提示库存不足 |
| 12 | 「清空明细」/「删除」某行 | 生效，扫码时间列随之清空 |
| 13 | 「保存草稿」 | 返回列表，状态=**草稿**，库存不变 |

## 五、状态机速查（用于核对列表状态列）

| 单据 | 状态流转 | 库存影响时机 |
|---|---|---|
| 入库单 | 草稿 → 待审核 → 已入库；草稿/待审核 → 已作废 | **审核通过**时增加库存，按件追踪配件生成库存件 |
| 出库单 | 草稿 → 待审核 → 已出库；草稿/待审核 → 已作废 | **审核出库**时扣减库存，库存件转为已出库 |
| 调拨单 | 草稿 → 已调出 → 已调入；草稿/待审 → 作废 | **确认调出**扣减调出仓；**确认调入**增加调入仓 |
| 盘点单 | 草稿 → 盘点中 → 已完成；草稿 → 作废 | **完成盘点**时按差异调整 |
| 维修工单 | 待修 → 维修中 → 已完工 → 已结算 | 不直接改库存；领料出库时累加配件成本 |
| 库存件 | 在库 → 锁定 → 已出库 / 已报废 / 已盘亏 | 由出库、盘点、报废操作驱动 |

## 六、常见「看起来像 bug，其实是预期」的点

1. **入库流水落在配件维度，出库流水落在库存件维度** —— 查流水时按单号查，不同单据的明细维度不同，属正常设计。
2. **盘点快照里按件追踪配件的实盘数初始为 0** —— 必须逐件扫码才算「已盘」；前端对未盘行不显示差异，完成盘点时未扫到的件按盘亏处理，这是设计如此。
3. **只读账号仍能看到「用户管理」菜单** —— 前端菜单未按角色过滤，权限在后端拦截，验收标准是「操作被拒绝且有提示」。
4. **空明细出库单可以保存为草稿** —— 只拦「提交审核」，草稿允许暂存。
5. **库存查询没有导出按钮** —— 导出在「配件列表」和「库存报表」页；不要误判为缺失。
6. **盘点只在「完成」时改库存** —— 盘点中看到库存未变是正常的。
7. **首页「低库存配件」按可用数量（库存−锁定）判定** —— 有锁定量时可能比账面数量先触发低库存。

## 七、清理与回归

**本轮测试结束后**（保留数据便于复查，只清理明显垃圾）：
1. 作废所有测试单据（草稿/待审状态的入库、出库、调拨、盘点）。
2. 删除测试用户（`MAN-*`）。
3. 库存归零后删除测试库位、测试仓库、测试车辆、测试供应商、测试配件（顺序：单据 → 库存件 → 配件 → 分类）。
4. 保留已结算工单与报表数据，供单车成本核对。

**每轮回归的最短主干（约 20 分钟）**：
登录 → 建测试配件 → 入库（扫码 1 件 + 手工 1 行）→ 提交 → 审核 → 库存查询核对 → 建工单 → 开始维修 → 出库扫码（关联工单）→ 审核出库 → 工单详情看配件成本 → 完工 → 结算 → 库存报表核对 → 流水报表按单号核对 → 单车成本核对 → 操作日志确认有记录 → 只读账号验证写操作被拒。

**配套自动化**：后端已有真实服务端到端冒烟用例 `backend/tests/test_e2e_live.py`（覆盖本文档主干链路），手工测试用于补充 UI 交互、扫码枪、打印与权限体验等自动化难以覆盖的部分。
